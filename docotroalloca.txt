Doctor Allocation Engine — Build Specification

GOAL
Build a production-ready doctor allocation system for the SOS workflow.

The SOS is created by a VERIFIED healthcare worker, not by the patient.

FLOW

Healthcare Worker
→ creates SOS
→ attach worker verified profile + mobile + current location + patient case
→ backend creates SOS
→ allocation engine finds eligible doctors
→ rank doctors
→ notify selected doctors
→ first valid acceptance wins
→ assign doctor
→ notify healthcare worker
→ doctor can contact the healthcare worker

CORE PRINCIPLE

Doctor allocation must NOT simply select the nearest doctor.

Allocation should consider:
1. Doctor verification
2. Real-time availability
3. Working schedule
4. Medical speciality / case relevance
5. Distance from healthcare worker
6. Doctor workload / current active SOS count
7. Doctor response history
8. Escalation if nobody accepts

--------------------------------------------------
2. HEALTHCARE WORKER SOS
--------------------------------------------------

The worker sends:

POST /api/sos

Example:

{
  "patient_id": "...",
  "case_description": "Patient has severe breathing difficulty",
  "severity": "HIGH",
  "required_speciality": "PULMONOLOGY",
  "latitude": 26.4499,
  "longitude": 80.3319,
  "location_accuracy": 8.5
}

The backend should derive the worker identity from the authenticated token.

Do NOT trust client-submitted worker_id.

The SOS should also store a snapshot/reference of the worker's verified profile.

The doctor should receive:
- Worker name
- Verified badge
- Worker role
- Worker mobile number
- Current location
- Clinic/facility
- Patient case summary
- Severity
- Images/video if attached


--------------------------------------------------
3. ELIGIBLE DOCTOR FILTER
--------------------------------------------------

Before calculating a score, remove doctors who should NOT receive the SOS.

Doctor must:

✓ verification_status = VERIFIED
✓ be inside their working schedule OR explicitly marked available
✓ presence.status = AVAILABLE
✓ heartbeat must be recent
✓ not already exceed active SOS workload limit
✓ match required speciality when speciality is critical
✓ not be suspended
✓ have valid notification token

Example:

if doctor is:
VERIFIED + AVAILABLE + heartbeat < 90 sec
→ eligible

If heartbeat is older than 90 seconds:
→ treat as OFFLINE


--------------------------------------------------
4. DOCTOR ALLOCATION SCORE
--------------------------------------------------

Do not hard-code one permanent formula forever.

Start with:

speciality_score = 50
availability_score = 20
distance_score = 20
workload_score = 10

Total = 100

Example:

Speciality:
Exact match = 50
Related speciality = 30
General doctor = 15
No match = 0

Availability:
AVAILABLE = 20
BUSY = 0

Distance:
0–2 km = 20
2–5 km = 15
5–10 km = 10
10–20 km = 5
>20 km = 0

Workload:
0 active SOS = 10
1 active SOS = 7
2 active SOS = 3
3+ active SOS = 0

IMPORTANT:
For HIGH/CRITICAL cases, speciality compatibility should be a hard requirement where possible, not merely a score.


--------------------------------------------------
5. LOCATION
--------------------------------------------------

Use the healthcare worker's current location as the primary routing point.

Do NOT require the patient to have a phone or GPS.

The worker's mobile device sends:
latitude
longitude
accuracy
timestamp

Use PostGIS/geospatial queries if using PostgreSQL/Supabase.

The system should be able to query:

"Find verified available doctors within 5 km."

Then expand:

5 km → 10 km → 20 km

only if required.


--------------------------------------------------
6. RING-BASED ALLOCATION
--------------------------------------------------

Do NOT send every SOS to every doctor.

Use controlled waves.

Wave 1:
Top 3 eligible doctors.

Wait 15 seconds.

If nobody accepts:

Wave 2:
Next 5 eligible doctors.

Wait 15–20 seconds.

If nobody accepts:

Wave 3:
Expand search radius and notify additional eligible doctors.

If nobody accepts:

Mark SOS as ESCALATED.

Notify clinic/admin/emergency escalation channel.


--------------------------------------------------
7. FIRST ACCEPTANCE WINS
--------------------------------------------------

This is critical.

Multiple doctors may receive the same SOS.

Only ONE can become the assigned doctor.

Use an atomic database update / transaction.

Concept:

UPDATE sos_requests
SET status = 'ASSIGNED',
    assigned_doctor_id = doctor_id
WHERE id = sos_id
AND status IN ('OPEN', 'ALLOCATING');

If the update succeeds:
doctor won.

If it affects zero rows:
someone else already accepted.

Never rely only on frontend checks.


--------------------------------------------------
8. ACCEPT / DECLINE API
--------------------------------------------------

POST /api/sos/{sos_id}/accept

Backend must verify:

✓ doctor is authenticated
✓ doctor is verified
✓ doctor is still eligible
✓ SOS is still OPEN/ALLOCATING
✓ doctor received the SOS
✓ atomic assignment succeeds

Then:

SOS → ASSIGNED
assigned_doctor_id → doctor

Immediately notify:
Healthcare Worker
Other notified doctors


POST /api/sos/{sos_id}/decline

Record:

doctor_id
reason (optional)
timestamp

Then continue allocation.


--------------------------------------------------
9. REAL-TIME DOCTOR PRESENCE
--------------------------------------------------

Doctor app must provide:

POST /api/doctor/presence

{
  "status": "AVAILABLE"
}

And heartbeat:

POST /api/doctor/heartbeat

Every 30–60 seconds.

If no heartbeat for 90 seconds:

AVAILABLE → OFFLINE

When doctor becomes busy:

AVAILABLE → BUSY

When doctor finishes:

BUSY → AVAILABLE

--------------------------------------------------

--------------------------------------------------
13. LOCATION SHARING
--------------------------------------------------

When SOS is active:

Worker location:

longitude

accuracy

Do not continuously expose location after the SOS is closed.

When:

SOS → RESOLVED/CANCELLED

stop live location sharing.


--------------------------------------------------
14. SECURITY
--------------------------------------------------

Important:

✓ Healthcare worker must be authenticated.
✓ Worker profile must be verified.
✓ Doctor must be verified.
✓ Role-based access control.
✓ Doctors can only access SOS requests they received/are assigned to.
✓ Workers can only access their own SOS requests.
✓ Never expose unnecessary patient information.
✓ Encrypt sensitive data in transit.
✓ Keep audit logs.
✓ Rate-limit SOS creation.
✓ Prevent duplicate SOS requests.
✓ Validate GPS coordinates.
✓ Do not trust worker_id/doctor_id from frontend.

--------------------------------------------------
16. ALLOCATION SERVICE
--------------------------------------------------

Create one central function:

allocate_doctor(sos_id)

Responsibilities:

1. Load SOS
2. Find eligible doctors
3. Filter by verification
4. Check schedule
5. Check presence
6. Check heartbeat
7. Check speciality
8. Calculate distance
9. Calculate workload
10. Calculate score
11. Sort candidates
12. Save candidates
13. Send first notification wave
14. Start escalation process


--------------------------------------------------
17. BACKGROUND JOBS
--------------------------------------------------

Use a background worker/queue.

Recommended:

FastAPI
+

+

       ↓

       ↓

       ↓

--------------------------------------------------
19. IMPORTANT EDGE CASES
--------------------------------------------------

Handle:

- Doctor goes offline after receiving SOS
- Doctor accepts after another doctor already accepted
- Worker cancels SOS
- Doctor declines
- Doctor loses internet
- Push notification fails
- No doctors available
- Doctor becomes busy while SOS is being allocated
- Worker changes location
- Duplicate SOS
- Two workers request help for the same patient
- Database/network failure during acceptance


--------------------------------------------------
20. FINAL PRODUCT BEHAVIOUR
--------------------------------------------------

The system should ultimately behave like:

Healthcare Worker
       ↓
Verified identity
       ↓
Current location
       ↓
Patient case
       ↓
SOS
       ↓
Allocation Engine
       ↓
Verified + Available + Suitable Doctors
       ↓
Rank by speciality + distance + workload
       ↓
Notify best candidates
       ↓
First valid acceptance wins
       ↓
Doctor assigned
       ↓
Worker gets doctor contact
       ↓
Doctor gets worker location/contact
       ↓
SOS resolved
       ↓
Assignment + audit history stored

BUILD THIS ALLOCATION ENGINE AS A SEPARATE MODULE.
Do not tightly couple doctor allocation logic to the frontend or the SOS UI.
